## Step 1：核心前置动作

1. 获取当前系统日期（YYYY-MM-DD）
2. **格式转换**：执行 `.venv/Scripts/python.exe scripts/convert.py --inbox`，将 INBOX 中的非 Markdown 文件（PDF/DOCX/PPTX/XLSX/EPUB/HTML/CSV/图片等）通过 MarkItDown 统一引擎自动转为 Markdown（⚠️ 必须用项目 venv 的解释器：裸 `python` 可能指向宿主环境、缺 pytesseract/markitdown，图片 OCR 会静默失效）。转换后的 .md 文件与原文件共存于 INBOX 中。**同时自动检测英文 .md 文件，调用 Google Translate 翻译为中文，生成 `.zh-cn.md` 同名文件**。编译时优先使用中文版（`.zh-cn.md`），英文原文照常归档 `raw/`
- **入口链接查重（2026-08-17 新增）**：对 `00-INBOX/` 中带来源链接的文件，先按 URL 归一化判重；同一链接已入库则跳过。
   - 抖音链接（v.douyin.com / douyin.com/video/）：解析 video_id → 查 `.llm-wiki/douyin_ledger.db` 账本 + `raw/douyin/` 下 .md 的 frontmatter `video_id`（短链与长链按 video_id 判重，字符串匹配不上）
   - 其他平台：规范化链接（去尾部斜杠/#fragment/utm_*）→ 查 `raw/` 所有 .md 的 frontmatter `source:` 精确匹配 + 00-INBOX 其他文件 source
   - **命中 = 该链接已入库/排队中 → 跳过该文件**，向用户汇报「重复跳过：文件 + 已存在于何处」；未命中才进入编译
   - ⚠️ 去重匹配层是 `raw/`（转录稿/抓取内容 frontmatter source=真实链接），不是 `wiki/`（编译产物 source=平台名）
4. 预扫描 `wiki/ideas.md`（待深挖灵感池）中的话题列表
5. **读取知识库上下文**（两步编译关键输入）：
   - 读取 `system/COMPILE.md`（双轨编译规则与模板 — 编译产出的结构必须严格遵循此文件的模板 A/B）
   - 读取 `wiki/index.md`（已有页面索引）
   - 读取 `wiki/overview.md`（全库综合概述）
   - 读取 `purpose.md`（知识库目的声明）

## Step 2：分析与关系判定

对 `00-INBOX` 中的每个新文件执行：

1. **读取源文件**：如果是子文件夹，将所有内容联合读取视为一个整体。
   - **图文笔记归类（2026-08-21，配合平铺布局）**：INBOX 中 `{标题}.md` 与旁同名前缀的 `{标题}_img_N*.md`（convert.py 对平铺图片的 OCR 产物）视为**同一篇文章**——编译时把各 `_img_N*.md` 的 OCR 文本合并进该笔记的编译产物（正文常在图里，合并后图内文字才可被检索）；`{标题}_img_N*.md` 是中间文件，**不单独编译成独立 wiki 页**；原图 `{标题}_img_N.jpg` 归档 `raw/assets/`。
2. **增量核对**：读取 `✅ processed.md`，跳过已处理文件
3. **结构化分析**（输出分析结果，不直接生成文档）：
   - 这篇文章讲了什么？提取核心概念列表（⚠️ **概念判定标准**：只有同时满足 3 条硬性条件才标记为概念——①抽象性：可复用的思维模型/认知框架/原理，不是具体事物；②可复用性：能跨场景迁移解释新现象；③可定义性：有明确的一句话定义。**排除清单**：工具名/产品名/人名/项目名、单一事件、纯操作步骤。一篇文章可以零概念，不硬凑）
   - 和知识库已有内容有什么关系？对照 `wiki/index.md` 和 `wiki/overview.md`：
     - 哪些概念在知识库中已存在？→ 标记为已有概念，后续只建双链不新建页面
     - 哪些概念是新的？→ 标记为待创建
     - 有没有和已有观点矛盾的地方？→ 标记矛盾点
   - 与已有文档的关系分类（判断新文档与搜索到的已有总结文档属于哪种关系）：
     - **引用**：提到了已有概念，但未扩展内容 → 只建双链
     - **补充**：扩展了已有文档未覆盖的方面 → 标记为待自动融入已有文档
     - **推翻/矛盾**：与已有文档观点冲突 → 标记矛盾点
     - **对比**：同一主题不同角度 → 标记为平行视角
     - **时序/演化**：同一话题的后续发展 → 标记演化关系
     - **包含/层级**：子集或超集关系 → 标记层级关系
   - 这篇文章适合哪个 category？→ 判定分类路由

## Step 3：双轨编译与生成

基于 Step 2 的分析结果执行：

1. **重命名与移动**：按 `YYYY-MM-DD_HHmm_类型_标题.md` 格式重命名，移动至 `raw/` 对应子文件夹。**若源文件为非 Markdown 格式（图片/PDF/DOCX/PPTX 等），原文件归档至 `raw/assets/`，仅保留 convert.py 生成的 .md 进入编译流程**
2. **选择模板（三轨分流，先看内容形态再看篇幅）**：
   - 提示词/个人感想/清单/SOP/模板文件/工具说明 → `COMPILE.md` 模板 C（产物形态：用途→结构→用法→关联）
   - 视频/音频/长篇访谈逐字稿、深度长文（>150行或结构明显）→ `COMPILE.md` 模板 B
   - 碎片笔记、短文、普通文章 → `COMPILE.md` 模板 A
3. **生成编译文档**：基于 Step 2 分析 + COMPILE.md 模板，生成总结文档
   - **物理路由**：读取 YAML 的 `category`，保存至 `wiki/summaries/[category]/`
   - **自动化挂靠**：注入当前日期与来源信息
   - **关联文档写入**：在编译文档的「核心概念与关联」区，根据 Step 2 的关系分类写入关联信息：
     - **引用**关系 → 写入已有概念双链（已有机制）
     - **补充**关系 → 写入已有文档双链并注明"本文补充了 XXX 方面"
     - **对比**关系 → 写入已有文档双链并注明"与本文为不同角度"
     - **时序/演化**关系 → 写入已有文档双链并注明"本文为 XXX 的后续发展"
   - **Unlinked References 检测**：扫描编译文档正文中出现了已有文档标题或概念名但未建双链的位置，自动补链（零LLM，纯模式匹配）
4. **概念页面处理**（蒸馏自 obsidian-second-brain ingest）：
   - **新概念**：在 `wiki/concepts/` 新建独立 .md 文件并完善定义
   - **已有概念**：如果新文章**补充了已有概念的新信息** → **重写**概念页（合并新旧信息），不是追加！如果只是引用 → 只生成双链，不修改原有文件
5. **矛盾处理**（蒸馏自 obsidian-second-brain reconcile）：
   - 如果 Step 2 发现矛盾 → 在总结文档的矛盾区标记
   - 尝试给出解决方案（适用场景不同？时代背景不同？）
   - 提示用户可用 `#lint` 进行差异扫描
6. **状态标记**：将编译文档的 YAML `status` 设为 `compiled`

## Step 3.5：实体索引写入

对每个新生成/更新的 wiki 页面，执行 `.venv/Scripts/python.exe scripts/entity_index.py --file <wiki页面路径>`：
- 内部会提取 event_text（一句话核心概括）+ 概念列表 + 推断 role（core/mention），写入 entity_index.db
- 概念页也会被索引：event_text 取第一段定义，实体取底部来源双链指向的其他概念
- 此步骤零额外 LLM 调用，复用编译时已有的概念提取输出
- 如果 entity_index.py 执行失败，不影响编译结果，仅影响搭桥搜索

## Step 4：向量化与 Zvec 入库（RAG 索引）

编译完成后，对每个新生成/更新的 wiki 页面执行：
1. **生成向量**：执行 `PYTHONPATH="" .venv/Scripts/python.exe scripts/embed.py --file <wiki页面路径>`，用 fastembed 本地 ONNX 推理生成 embedding 向量
2. **Zvec 入库**：embed.py 内部会将向量+FTS索引一起 upsert 到 Zvec
3. **验证**：执行 `PYTHONPATH="" .venv/Scripts/python.exe scripts/search.py "页面标题关键词" --top 3`，确认新页面可被检索到

注意：
- embed.py 会临时加载模型（峰值~650MB内存），生成完自动释放到~80MB
- 如果 embed.py 执行失败，不影响编译结果，仅影响搜索索引（下次全量索引可修复）
- 全量索引可在任何时候用 `PYTHONPATH="" .venv/Scripts/python.exe scripts/embed.py` 重建

## Step 6：增量关联与进化

对每个新入库的页面，执行 `PYTHONPATH="" .venv/Scripts/python.exe scripts/search.py "新文档标题关键词" --top 5 --backend zvec`，逐一检查搜索结果中的已有文档与新文档的关系：

### ⚠️ 双链建链铁律（2026-08-02 修订）

**双链只建在"内容主体真实相关"的关系上，不建在"分数碰巧高"的擦边上。**

1. **相似度分数只是召回工具，不是建链判据**——分数负责把候选文档捞出来，建不建链由 AI 判定关系类型决定
2. **可建链的关系只有 5 种，且必须有信息增量**（见下表）。5 种关系都不是 → **不建链，静默跳过**
3. **>0.8 高相似归入 Step 5 语义去重**（接近重复 = 该合并确认，不是该链接）
4. **每条链必须带关系类型注释**（"本文补充了XXX" / "同主题互证"等），供 #lint 逐条验证，错链可定位清除

### 关系分类与自动执行动作

| 关系 | 判定条件（必须满足内容主体真实相关） | 执行动作 | 自动/确认 |
|------|---------|---------|----------|
| **补充** | 新文档提供了已有文档未覆盖的信息 | ①已有文档正文自动融入新信息（重写对应段落） ②新文档加已有文档双链并注明"补充了 XXX" | ✅ 全自动 |
| **推翻/矛盾** | 新文档与已有文档观点冲突 | 新文档矛盾区标记，提示 `#lint` | ✅ 全自动 |
| **对比** | 同一主题不同角度 | 新文档加已有文档双链并注明"不同角度"，已有文档加反向双链 | ✅ 全自动 |
| **时序/演化** | 同一话题的后续发展 | 新文档加已有文档双链并注明"后续发展"，已有文档加反向双链 | ✅ 全自动 |
| **同主题互证** | **两篇内容主体是同一主题，内容高度相似可互相印证** | 双向自动建双链并注明"同主题互证" | ✅ 全自动 |
| **无关系**（含主题擦边：只是片段提到相关词/概念，主体不同） | 以上 5 种都不是 | **不建链，静默跳过** | — |

### 自动进化规则

- **补充关系**：将新信息直接融入已有文档正文的对应位置（重写而非追加），与概念页重写合并逻辑一致
- **双向建链**：新文档指向已有文档 + 已有文档对话沉淀区追加关联记录
- **融合后更新索引**：已有文档被改写后，重新执行 `PYTHONPATH="" .venv/Scripts/python.exe scripts/embed.py --file <文档路径>` 更新向量索引
- **质量兜底**：每周自动审查（见 `#lint` 定期审查模式），检查自动变更的质量，发现问题自动修正

## Step 8：弱关联提醒（增量织网）

对新入库的文档，发现 Step 6 未覆盖到的弱关联：
- **弱关联发现**：用 Zvec 搜索新文档的语义相关文档对（相似度 0.4-0.6 区间，作为召回候选）
- **关联建议**：将匹配结果以列表形式呈现给用户确认，给出关联理由（⚠️ 候选仍需符合双链铁律的 5 种关系之一——补充/推翻/对比/时序/同主题互证，主题擦边不推荐）
- **双链生效**：确认后写入双链，下次搜索自动生效
- **auto-link 提取双链（零LLM）**：写入源文件时，自动提取所有双链。搜索时实时计算双链邻居关系，无需额外图谱文件。此步骤零 LLM 调用，纯模式匹配

与 `#bridge` 的区别：Step 8 只看新文档的增量关联（入库时零额外搜索成本），`#bridge` 做全库扫描（需手动触发）。
