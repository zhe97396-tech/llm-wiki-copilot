# 🔍 知识库差异扫描：`#lint` 或 `#纠错`

**核心定位**：发现差异，分级标注。日常差异只标注不修改，自动进化内容的审查发现问题则自动修正。

**触发来源**：
1. 用户主动执行 `#lint`
2. `#ingest` Step 6 检测到**推翻/矛盾**关系时自动标记，提示用户用 `#lint` 深度扫描
3. 定时任务自动扫描（差异扫描 + 自动审查）

## 三种使用模式

| 模式 | 触发方式 | 说明 |
|------|---------|------|
| **自动扫描** | `#lint`（无参数）或定时任务触发 | 全库扫描，机械检查+差异扫描 |
|| **指定比对** | `#lint 文档A 文档B` | 对指定文档深度比对 |
| **自动审查** | 定时任务（每周） | 审查最近7天自动进化的内容质量，发现问题自动修正 |

## 差异分级体系

| 等级 | 标签 | 含义 | 举例 | AI动作 |
|------|------|------|------|--------|
| 🔴 事实冲突 | `CONFLICT` | 同一事实，数据/结论对不上 | A说"短视频停留1.5秒"，B说"8秒" | 标注，需人工核实 |
| 🟡 视角差异 | `PERSPECTIVE` | 同一主题不同角度，都成立 | A从宏观说"个人无法对抗"，B从微观说"可以慢速内容应对" | 标注"场景不同，可共存" |
| 🟠 定义分歧 | `DEFINITION` | 同一概念不同定义/内涵 | A定义注意力经济=剥削，B定义=筛选机制 | 标注，建议统一或注明语境 |
| 🔵 时间演变 | `TEMPORAL` | 旧说法被新信息更新 | 2024年的数据被2026年推翻 | 标注"旧信息可能过时" |
| ⚪ 内部不一致 | `INTERNAL` | 同一篇文章内自相矛盾 | 前半段说X，后半段说非X | 标注，可能是编译疏漏 |

## 执行流程

### Step 1：机械检查（0 LLM，复用 health.py）

运行 `PYTHONPATH="" .venv/Scripts/python.exe scripts/health.py`，检查：
- 断链（`[[X]]` 指向不存在的页面）
- 空文件
- 索引不同步
- 孤儿页面
- Frontmatter 缺失

### 孤儿页处理原则（2026-08-10 用户确认）

孤儿页 = 无任何入链的页面。**是孤儿就是孤儿，不为了消除孤儿而强行建链**；但**规范要求存在的链缺失了则必须补**。判断标准：

| 情形 | 处理 |
|------|------|
| 概念页来源缺双链（规范要求 `> 来源：[[宿主总结页]]`，实际只写文字） | 🔴 **必补**——这是编译漏链，补上即消除孤儿 |
| 索引型文件（type: topic-index，如延伸话题库）无入链 | ✅ 属正常设计，不补 |
| 页面与全库确实无真实关联 | ✅ 保持孤儿，等未来自然关联（符合双链铁律：无关系不建链） |

**红线**：不为消除孤儿而创建低关联双链（关联度低=硬凑=违反双链铁律）。

### Step 2：差异扫描（AI + 向量）

1. **向量预筛**：用 Zvec 找语义相似度 0.6-0.95 的文档对（说了差不多的事但说法可能不同）
2. **LLM 交叉阅读**：对预筛出的文档对 + 全库概念页，按5级分类标注差异
3. **内部一致性**：检查单篇文章内是否存在自相矛盾

### Step 3：输出报告

格式：
```
📊 知识库差异扫描报告

【机械检查】
- 断链：N处
- 孤儿页面：N个
- 索引不同步：N条
- ...

【差异标注】
🔴 CONFLICT | 文档A vs 文档B
   A说"X"，B说"Y" → 需人工核实

🟡 PERSPECTIVE | 文档A vs 文档B
   A从宏观角度，B从微观角度 → 场景不同，可共存

🟠 DEFINITION | 概念X 在 文档A vs 文档B
   A定义为...，B定义为... → 建议统一或注明语境

🔵 TEMPORAL | 文档A（2024）vs 文档B（2026）
   旧说法"X"被新信息"Y"更新 → 旧信息可能过时

⚪ INTERNAL | 文档A 内部
   前半段说X，后半段说非X → 可能是编译疏漏

【无差异】✅ 其余文档无冲突
```

## 定时扫描模式（可选；宿主支持定时任务时才可用）

- 周期：每周一早上9点
- 交付：在对话中展示报告（不生成文件）
- 行为：Step1机械检查 + Step2差异扫描 → 分级报告推送
- 后续：用户确认后才执行修改，AI不自作主张改知识库

## 自动审查模式（自动进化质量兜底）

**目的**：Step 6 自动进化（补充融入正文、自动建链）可能改错，定期审查兜底。

**触发**：每周定时任务，在差异扫描之后执行。

**审查范围**：最近7天内被自动进化修改过的文档（通过 `wiki_log.md` 中标记为 `自动进化` 的记录定位）。

**审查流程**：

### Step 1：定位变更文档
读取 `wiki_log.md`，筛选最近7天带 `🔄 自动进化` 标记的条目，获取被修改的文档列表。

### Step 2：逐文档质量审查（LLM）
对每个被修改的文档，LLM 检查：
1. **补充准确性**：自动融入的新信息是否准确、是否放在了正文正确位置
2. **双链合理性**：自动建的双链是否真的相关，有无错误关联
3. **信息完整性**：重写段落时是否丢失了原有信息
4. **概念页一致性**：概念页重写后定义是否与引用它的总结文档一致

### Step 3：自动修正
- **确定有问题**（信息丢失、双链错误）→ 自动修正：回退错误变更、删除错误双链、补回丢失信息
- **不确定**（补充信息可能不准确但无法确认）→ 标记为 ⚠️ 待确认，推送给用户
- **无问题** → 静默通过，不推送

### Step 4：审查报告
仅推送有问题的条目（自动修正的 + 待确认的），格式：
```
🔍 自动审查报告（YYYY-MM-DD）

【已自动修正】
- 文档A：补充信息位置不当，已调整至"关键知识点"区
- 文档B：错误双链，已删除

【⚠️ 待确认】
- 文档C：补充的"XXX"数据无法验证准确性，请核实
```

## 红线

1. **差异扫描只标注不修改**：日常差异扫描发现的问题只报告，不自动修改任何文件
2. **自动审查可修正**：自动进化引入的问题，审查时可以自动修正（因为是修正自动操作，不是修改用户原始内容）
3. **不确定的不自作主张**：审查中拿不准的问题标记为 ⚠️，交给用户判断
4. **不判对错**：视角差异和定义分歧不代表谁错，只是不同
